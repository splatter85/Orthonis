# Foundation usage and Windows handoff

Document ID: `orthonis.doc.foundation-guide`.

## What this build does

This is a developer-facing CLI demonstration, not a desktop PC scanner. It produces synthetic Startup and Reliability evidence through the same interfaces intended for later Windows adapters. It writes its own local case files, but does not modify Windows configuration, registry entries, services, or applications. No model service is called by any command.

Use the selected SDK in [global.json](../global.json), build the solution, then run the [verification commands](PROJECT_HEALTH.md). The C# regression suite is an executable harness run with `dotnet run`, not a test-discovery project invoked with `dotnet test`.

## Persistent demonstration

From the repository root:

```sh
dotnet build Orthonis.slnx --configuration Release
dotnet run --project src/Orthonis.Cli --configuration Release --no-build -- start .local/demo missing
dotnet run --project src/Orthonis.Cli --configuration Release --no-build -- report .local/demo
```

Other source scenarios are `healthy`, `denied`, and `inconclusive`. These are fixture names, not diagnoses of the host computer. The missing scenario first records two startup items whose target presence is not yet checked, plus repeated synthetic application hangs. A later targeted inspection reveals the missing fixture target. The app does not infer that the missing target caused those hangs.

A saved case is `.local/demo/case.json`. Reusing that directory with `start` is refused. Case identifiers, collection timestamps, and evidence IDs are generated by the program. The same saved snapshot retains the same hash when reloaded. Reports contain an editable discovery-plan example with a new plan ID.

## Manual report and return-plan exchange

Run `report` and copy its complete Markdown output to an AI chat. It includes the source label, evidence, findings, actual available capabilities, return instructions, and a case-bound example. Ask the reviewer to distinguish observations from hypotheses and request supported read-only follow-up work. Save its returned JSON object as UTF-8 without a byte-order mark, without Markdown fences, for example `.local/plan.json`.

To obtain an example locally without using any AI service:

```sh
dotnet run --project src/Orthonis.Cli --configuration Release --no-build -- example-plan .local/demo
```

Copy the JSON to a file in an editor configured for UTF-8. Do not assume an older shell's output redirection uses that encoding. The strict importer refuses unsupported encoding rather than guessing.

Preview first:

```sh
dotnet run --project src/Orthonis.Cli --configuration Release --no-build -- apply .local/demo .local/plan.json
```

Preview validates the complete plan and prints its requested operations. It runs no collectors and does not change the case revision. Inspect those operations, then explicitly approve:

```sh
dotnet run --project src/Orthonis.Cli --configuration Release --no-build -- apply .local/demo .local/plan.json --approve
```

An accepted plan collects fixture evidence, saves one new case revision and its applied-plan ID, and prints a follow-up report. Reusing an old plan is refused. Export a fresh report before another round. The local `--approve` flag is required; a JSON `approved` field cannot supply authority and is rejected as unknown.

Exit codes: 0 success or preview, 2 refused input/request, 3 cancelled, 4 storage unavailable/busy/permission failure. A failure is not a healthy finding. Following a storage error, reload the case to establish its actual state before retrying.

## Version 1 proposal contract

The actual [DiscoveryPlan type and validator](../src/Orthonis.Core/DiscoveryPlans.cs) own the format. Required fields are `schemaVersion`, `kind`, `planId`, `caseId`, `basedOnRevision`, `basedOnSnapshotHash`, `hypothesis`, `evidenceRefs`, and `requests`. `kind` must be `discovery`; schema version is 1. Each request has `capabilityId`, `capabilityVersion`, and `targetId`, including explicit null for an untargeted capability.

The supported operations are `startup.inventory`, `startup.inspect`, `reliability.summary`, and `reliability.inspect`, all version 1. Targeted operations require an observed target from the matching module and target kind. The concrete report/example supplies identifiers instead of expecting the reviewer to guess them. No file paths, shell text, executable scripts, repair actions, or new capability definitions are accepted as requests.

Input limits include 64 KiB per proposal, JSON depth 16, 1 to 8 requests, and 1 to 32 unique evidence references. Cases use schema 1, at most 2 MiB, and bounded revisions/evidence counts. Unknown fields and versions, duplicate JSON keys, invalid/non-finite values, missing required fields, wrong cases, stale revision/digest, unknown targets, duplicate requests and applied-plan replay are refused before collector calls. The hash binds the saved representation; it is neither authentication nor proof of diagnostic correctness.

## Storage and trust limits

The file store supports one cooperating writer with a case-directory lock, checked revision, and same-directory temporary-file replacement. Tests inject a failure before replacement and verify unchanged readable prior bytes. This does not establish power-loss durability, universal transactional repair, a hostile-filesystem sandbox, or protection against a local administrator. The store refuses observed linked/reparse paths, but stronger race-proof Windows confinement is later work.

Modules are trusted built-in code. Cancellation budgets do not make in-process code a sandbox or guarantee termination of a noncooperating collector. Reports export all retained synthetic evidence; there is no tested redactor for real user data. Do not insert private data into a fixture case or mistake a synthetic label for proof of provenance. Plan parsing and explicit approval do not prove the AI's reasoning is correct.
